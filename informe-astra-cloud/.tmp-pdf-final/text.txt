1 Introduccin
    Las plataformas digitales de contenido integran diferentes funciones, como la gestin de usuarios,
catlogos, comunidades, interacciones y sesiones compartidas. A medida que estas funcionalidades
aumentan, tambin surge la necesidad de organizarlas de manera que puedan desarrollarse y
mantenerse de forma independiente.
    A partir de esta necesidad se desarroll ASTRA CLOUD, una plataforma cinematogrfica basada
en una arquitectura de microservicios. El proyecto integra seis servicios con responsabilidades
especficas y utiliza tecnologas cloud para su comunicacin, almacenamiento, despliegue y anlisis de
datos. En este informe se presenta la arquitectura implementada y los principales componentes
que permiten su funcionamiento.

2 Objetivos
2.1 Objetivo general
   Disear e implementar una plataforma cinematogrfica basada en microservicios, con servicios
backend, distintas bases de datos, contenedores Docker, infraestructura AWS y procesamiento
analtico.

2.2 Objetivos especficos
      Desarrollar servicios independientes para identidad, catlogo, comunidad, interaccin social,
      sesiones y analtica.

      Utilizar bases de datos relacionales y NoSQL segn el tipo de informacin de cada servicio.

      Ejecutar los componentes con Docker Compose y definir su despliegue como cdigo.

      Extraer datos operativos hacia S3 y habilitar consultas analticas mediante Athena.

3 Descripcin del proyecto
3.1 Problema y solucin
    En una plataforma cinematogrfica, la gestin de cuentas, pelculas, comunidades, reacciones y
sesiones compartidas responde a necesidades distintas y cambia a ritmos diferentes. Cuando estas
funciones se concentran en una sola aplicacin, las reglas de autenticacin, la informacin del catlogo,
la actividad social y la coordinacin en tiempo real quedan estrechamente acopladas. Esto dificulta
mantener cada parte, incorporar cambios y elegir la forma de persistencia ms conveniente para
sus datos.
    Para abordar esta situacin, ASTRA CLOUD adopta una arquitectura de microservicios.
Identity se encarga del registro y la autenticacin; Catalog administra la informacin de las pelculas;
Community organiza perfiles, clubes y salas; Interaction registra reseas, likes, listas e historial;
Cinema Session coordina las sesiones temporales; y Analytics consulta la informacin reunida
para fines analticos. La separacin permite delimitar responsabilidades y establecer integraciones
explcitas entre los servicios, sin perder la continuidad de la experiencia para el usuario.

3.2 Alcance
    El proyecto incluye las seis APIs de backend, sus configuraciones de contenedor, los procesos
de carga hacia S3 y la plantilla de infraestructura. Los cinco servicios de dominio requeridos por el
alcance se complementan con Identity, un servicio adicional y transversal de registro, autenticacin
y emisin de JWT. Esta separacin evita mezclar credenciales con las reglas del catlogo, comunidad,

4.2 Ruta de acceso
    Las solicitudes del cliente llegan primero a API Gateway y pasan al ALB interno mediante
VPC Link. El balanceador las dirige a la instancia EC2 y al contenedor donde se ejecuta el
servicio correspondiente. El ALB reparte las solicitudes entre las instancias disponibles y no queda
expuesto directamente a Internet.

5 Arquitectura de microservicios
    La solucin organiza cinco responsabilidades de dominio —Catalog, Community, Interaction,
Cinema Session y Analytics— y aade Identity como servicio transversal. Por ello se presentan
seis microservicios sin que ello altere el mnimo funcional: Identity concentra registro, autenticacin
y emisin de JWT, mientras que los dems servicios no almacenan ni administran credenciales. La
separacin reduce el acoplamiento entre identidad y lgica de dominio.

5.1 Identity Service
    Identity expone /api/auth/register y /api/auth/login. La tabla users guarda el UUID,
correo, nombre, hash de contrasea y rol. Al iniciar sesin, el servicio verifica la contrasea y emite
un JWT HS256 con sub, expiracin y emisor identity-service.

5.2 Catalog Service
    Catalog usa Spring Boot, Spring Data JPA y Flyway. Guarda pelculas, gneros, artistas, sus
relaciones, fuentes de video y subttulos. Sus rutas principales son /api/catalog/movies, /api/
catalog/home, /api/catalog/search y /api/catalog/movies/\{publicId\}/session-info.

5.3 Community Service
   Community usa FastAPI, SQLAlchemy y MySQL. Guarda perfiles asociados al UUID de
Identity, sin almacenar contraseas. Sus tablas son users, clubs, memberships, watch_rooms y
watch_participants. Las rutas bajo /api/v1 manejan perfiles, clubes, roles y salas.

5.4 Interaction Service
    Interaction usa Express, Mongoose y MongoDB. Sus colecciones reviews, likes, watchlists
y watch_history guardan cada accin junto con una copia de los datos del usuario y de la pelcula
en ese momento. Antes de guardar una accin, consulta Catalog y Community para validar las
referencias. La ruta /ingest/* entrega los datos por pginas para la extraccin.

5.5 Cinema Session Service
    Cinema Session guarda en memoria por proceso las sesiones, los participantes, el estado de
reproduccin y los ltimos mensajes del chat; al terminar la sesin ese estado se elimina. La ra-
ma integrada feature/http-polling-chat expone GET /api/v1/sessions/{id}/state, POST
/api/v1/sessions/{id}/chat y PATCH /api/v1/sessions/{id}/playback. La interfaz consul-
ta el estado cada 1,5 segundos, y usa las respuestas para volver a sincronizar el reproductor y el
chat. La ruta de estadsticas consulta Interaction por HTTP.

5.6 Analytics Service
   Analytics expone rutas bajo /api/v1, como /movies/top-watched, /interactions/movies/
best-rated y /dashboard/kpis. Con boto3, enva consultas SQL a Athena y devuelve las filas
como JSON.

5.7 Documentacin
   Las seis APIs desplegadas respondieron pblicamente a sus puntos de documentacin el 23 de
septiembre de 2026. Catalog publica /swagger-ui.html y /v3/api-docs; Identity, Community,
Cinema Session y Analytics exponen /docs y OpenAPI; Interaction integra Swagger UI en /docs.
La Tabla 5.2 identifica el artefacto remoto conservado, sin tokens ni cabeceras de autenticacin.

    El proyecto usa distintas bases de datos segun el tipo de informacion que maneja cada servicio;

movie_artist, fuentes de video y subtitulos. Las relaciones N:M entre peliculas, generos y artistas
se materializan mediante dichas tablas puente, y Flyway mantiene las versiones del esquema.

7 Comunicacin entre microservicios
    Los servicios se comunican por HTTP/REST. Identity entrega el JWT al iniciar sesin, y
Community, Interaction y Cinema Session revisan su firma antes de atender acciones protegidas.
Cuando Interaction guarda una accin, consulta Catalog y Community para validar la pelcula y el
usuario, y guarda una copia de esos datos junto con la accin. El navegador consulta peridicamente
el estado HTTP de la sesin y aplica la respuesta recibida.

8 Contenedorizacin
    Para desplegar los servicios se utiliz Docker. Docker Compose inicia Catalog en el puerto
8081, Community en 8000, Interaction en 8082, Analytics en 8002, Identity en 9000 y Cinema
Session en 8001. Todos comparten una misma red interna. Otro Compose inicia PostgreSQL 16,
MySQL 8.4.6 y MongoDB 7 con volmenes para conservar los datos. Los tres procesos que cargan
informacin a S3 tambin se ejecutan como contenedores y reciben por variables de entorno sus
conexiones y el destino en S3.

9 Infraestructura AWS
9.1 Red y cmputo
   CloudFormation define la red en AWS: una VPC 10.0.0.0/16, dos subredes pblicas en zonas
de disponibilidad diferentes, Internet Gateway, rutas y DNS interno. Tambin crea dos EC2 de
produccin, una para bases de datos y otra para ingesta, ambas t3.medium con volmenes gp3 de
20 GiB. La zona privada de Route 53 proycloud.local resuelve db.proycloud.local.

9.2 Exposicin de servicios

16 Flujos funcionales
16.1 Autenticacin y comunidad
    El cliente registra una cuenta o inicia sesin en Identity y recibe un JWT. Community revisa
el token y asocia el perfil local con el UUID sub. Despus, el usuario puede crear clubes, unirse a
ellos y abrir salas.

16.2 Catlogo e interacciones
    Catalog entrega las pelculas y sus datos. Cuando un usuario crea una resea, like, watchlist o
visualizacin, Interaction revisa el token, consulta los servicios necesarios y guarda la accin junto
con los datos relacionados.

16.3 Sesin y analtica
    Cinema Session coordina una sesin temporal mediante HTTP peridico: la pgina consulta GET
/state cada 1,5 segundos y actualiza el reproductor y el chat con la respuesta; los mensajes y
cambios de reproduccin usan POST /chat y PATCH /playback. Los contenedores de carga extraen
las tres bases de datos y suben archivos CSV a S3. Despus, Analytics consulta Athena para
obtener los indicadores.

17 Pruebas y validacin
    El proyecto incluye pruebas automatizadas para Community, Interaction y Cinema Session.
Community y Cinema Session usan Pytest para revisar rutas, permisos y flujos de salas. Interaction
usa node:test, Supertest y mongodb-memory-server, por lo que puede probar sus rutas sin una
instancia externa de MongoDB. Los servicios tambin tienen rutas de salud que usan la integracin
y el balanceo. Interaction incluye npm run seed, un script que puede ejecutarse varias veces sin
duplicar los datos que ya existen. Por defecto genera 20 000 documentos para reseas, watchlists e
historial, y 25 000 para likes. Las variables SEED_* permiten ajustar estos escenarios.

servicio administrado de secretos, monitoreo y alertas con CloudWatch, respaldos, Auto Scaling
Groups y CI/CD con pruebas y anlisis de imgenes. En la parte analtica, los procesos de Glue que
detectan la estructura de los archivos, las particiones y una programacin de cargas permitiran
ejecutar el proceso de forma peridica.

21 Conclusiones
    ASTRA CLOUD permiti implementar una plataforma cinematogrfica organizada en seis
microservicios con responsabilidades diferenciadas. Identity, Catalog, Community, Interaction,
Cinema Session y Analytics colaboran mediante interfaces definidas, lo que mantiene separadas
la autenticacin, el catlogo, la interaccin social, las sesiones compartidas y la consulta analtica.
    La solucin adopta persistencia polglota: PostgreSQL respalda las cuentas y el catlogo, MySQL
concentra la informacin comunitaria y MongoDB conserva las interacciones. Esta eleccin responde
al tipo de informacin administrada por cada servicio y se complementa con Docker y Docker
Compose para reproducir los entornos de ejecucin.
    El despliegue se describe con CloudFormation e integra VPC, instancias EC2, API Gateway,
VPC Link, ALB y S3. Adems, el flujo PostgreSQL/MySQL/MongoDB → CSV → S3 → Athena
permite analizar los datos extrados sin trasladar esa carga a las bases operativas. En conjunto, el
proyecto demuestra la integracin de servicios, persistencia, despliegue cloud y analtica dentro de
una arquitectura coherente para el alcance acadmico planteado.
